# Regenerating the 2D GLDZM oracle goldens

Offline; CI never invokes the generator. Run from the repository root.

## Environment

```
conda create -n nyxus_mirp -c conda-forge python=3.12 numpy
conda activate nyxus_mirp
pip install mirp==2.6.0
```

mirp exposes no `__version__`; read it with `importlib.metadata.version("mirp")`, which is what the
generator does. It also logs at INFO onto stdout, straight into the golden table — the generator
calls `logging.disable(logging.INFO)` before importing it.

## mirp — `test_2d_gldzm_mirp.h`

```
python tests/vetting/oracles/gen_gldzm_mirp.py
```

Expect `80 verified, 0 failed, 0 unproducible`. The generator prints both paste-ready tables, then
re-verifies every golden pinned in the header — the 16 four-slice means and the 64 per-slice values
— and exits non-zero on a mismatch or on a pin it cannot produce.

**Two tables, because a mean cannot vet the four values behind it.** mirp computes each slice on its
own; the averaging is the generator's, not the tool's. `gldzm_2d_mirp_slice_ref_vals` pins the
per-slice values (keyed `<feature>_z<slice>`) and `gldzm_2d_mirp_ref_vals` the means, and every
assertion checks both. This is not a formality on this family: the zone-connectivity defect the
re-vet found lived entirely in slice 1, and the four-slice mean diluted it by four.

**Fixture.** The four IBSI digital-phantom slices, read out of `tests/test_data.h` through
`oracles/ibsi_phantom.py`, so the generator and the C++ tests share one copy of the voxels.

**Config** (recipe `gldzm.ibsi_phantom_2d`):

```python
mirp.extract_features(image=slice_3d, mask=mask_3d, by_slice=True,
                      base_discretisation_method="none")   # phantom is already discrete 1..6
```

GLDZM takes no distance or coarseness parameter on either side — unlike NGLDM, whose generator must
pass `ngldm_distance` and `ngldm_difference_level` as floats. A GLDZM zone distance is a property of
the ROI mask, not a setting.

**Column mapping.** mirp's GLDZM columns end in `_2d` under `by_slice=True` and carry no
configuration suffix (contrast with NGLDM's `_d1_a0.0_2d`), so match the stem exactly:

| Nyxus | mirp | | Nyxus | mirp |
|---|---|---|---|---|
| `GLDZM_SDE` | `dzm_sde_2d` | | `GLDZM_GLNU` | `dzm_glnu_2d` |
| `GLDZM_LDE` | `dzm_lde_2d` | | `GLDZM_GLNUN` | `dzm_glnu_norm_2d` |
| `GLDZM_LGLZE` | `dzm_lgze_2d` | | `GLDZM_ZDNU` | `dzm_zdnu_2d` |
| `GLDZM_HGLZE` | `dzm_hgze_2d` | | `GLDZM_ZDNUN` | `dzm_zdnu_norm_2d` |
| `GLDZM_SDLGLE` | `dzm_sdlge_2d` | | `GLDZM_ZP` | `dzm_z_perc_2d` |
| `GLDZM_SDHGLE` | `dzm_sdhge_2d` | | `GLDZM_GLV` | `dzm_gl_var_2d` |
| `GLDZM_LDLGLE` | `dzm_ldlge_2d` | | `GLDZM_ZDV` | `dzm_zd_var_2d` |
| `GLDZM_LDHGLE` | `dzm_ldhge_2d` | | `GLDZM_ZDE` | `dzm_zd_entr_2d` |

Note mirp writes `lge`/`hge` where Nyxus writes `LGLZE`/`HGLZE`, and `perc`/`entr`/`var` where Nyxus
writes `P`/`ZDE`/`ZDV` — map by meaning, not by string similarity.

**Do not regenerate as oracle values:** `GLDZM_GLM` and `GLDZM_ZDM`. mirp has no grey-level-mean or
zone-distance-mean column because neither is an IBSI GLDZM feature. They are regression snapshots in
`test_2d_gldzm_regression.h`.

## IBSI consensus — `test_2d_gldzm_ibsi.h`

Those goldens are transcribed from the IBSI reference manual and are not regenerated by a tool. They
are quoted to **three significant figures**, which sets that file's `rel=1e-2` tolerance — the
measured worst case is 0.35% on `GLDZM_LDE` (1.21 published against 1.2142857 computed). Pin exact
digits against mirp instead; the two files are complementary.

**A published value has three significant figures.** Four entries in that table used to carry
sixteen, and all four were Nyxus' own output rather than transcriptions — two of them wrong by 5%
and 60%. If an entry cannot be found in the manual at the precision it is written, it is not an IBSI
value; see `gldzm_2d_ibsi_vetting_report.md`.

## The GLDZ-matrix reference — `ibsi_fig3_17c_gldzm_reference_matrix`

Pinned in `tests/test_data.h`, checked by `test_2d_gldzm_matrix_correctness_ibsi`. It is the
manual's figure 3.17 worked example: a 4x4 ROI, four grey levels by two zone distances. To re-derive
it, run mirp on that fixture and read the matrix off three features rather than trusting a
transcription:

```python
# img = [[1,2,2,3],[1,2,3,3],[4,2,4,1],[4,1,2,3]], mask all ones
dzm_z_perc_2d  = 0.5   # -> Ns = 0.5 * 16 = 8 zones
dzm_glnu_2d    = 2.25  # -> sum of per-grey zone counts squared = 2.25 * 8 = 18  (3,1,2,2)
dzm_zdnu_2d    = 6.25  # -> sum of per-distance zone counts squared = 50         (7 at d=1, 1 at d=2)
```

Those three pin the matrix uniquely. The table used to sum 9 zones, which none of them permits.

## Regression pins — `test_2d_gldzm_regression.h`

Not oracle values: Nyxus output for `GLDZM_GLM` and `GLDZM_ZDM` on the same phantom and recipe. To
re-record them after an intended math change, read the values off a run at those settings —
`gldzm_2d_phantom_slice_values(f)` averaged is the same call the test makes — and state in the PR
why the values moved. A drift guard re-pinned without that reason is not a guard.
